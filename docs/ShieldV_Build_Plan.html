ShieldV
Build Plan

An RV32IM processor that refuses to be hijacked, with two interchangeable cores: a 3-stage in-order pipeline (the committed baseline) and an out-of-order Tomasulo core (the extension), both protected by the same hardware shadow stack. Five people in three groups build against frozen interfaces and join one rung at a time, to the final demo (Nov 7–8).

Built in parallel, Oct 5 – Nov 1

Three groups, five owners

Each person owns one module end to end: the RTL, its testbenches and its explanation in the viva. They can be built at the same time because nobody waits on anybody: the connections between modules are frozen on day one as interface contracts, and every module is tested against stubs and its own testbench before it ever meets the others.

The interface contracts (frozen Oct 4, logged changes Oct 11)

These four port lists are the only things the modules share. Write them into docs/interfaces.md and a header file before any RTL. Changing one needs every owner of that interface to agree, with a line in the decision log.

// IF-1  Core <-> M-unit  (owner B implements, A calls)
input  start, input [2:0] op /*funct3*/, input [31:0] a, b,
output busy, output done, output [31:0] result
// rule: core stalls while busy; result valid when done=1 (1 cycle)

// IF-2  Core <-> Data bus  (A drives, B decodes)
output [31:0] addr, wdata, output [3:0] wstrb, output we, re,
input  [31:0] rdata            // available the next cycle

// IF-3  Core <-> ShieldV  (G1 exports, G3 consumes)
// in-order: from EX; out-of-order: from the ROB head at commit
output ex_valid    // real instruction, committing this cycle
output [31:0] ex_instr, ex_pc, ex_target, ex_link /*pc+4*/
input  sh_freeze, sh_trap, input [31:0] sh_handler_pc

// IF-4  Trace port  (A exports, B/C observe)
output [31:0] if_pc, ex_pc, wb_pc, output stall, flush, ex_valid,
output retire, branch, mispredict   // branch/mispredict added Oct 11

Why memory-mapped I/O: C code lights an LED or prints a character with an ordinary store instruction. No new instructions are needed, so the I/O can be built and tested without the CPU.

Joining the modules, Oct 16 – Nov 6

The integration ladder

Integration happens one rung at a time. Each rung swaps exactly one set of stubs for real blocks and has one gate test. If a rung fails you go back one rung, never more, because everything below it was already proven.

Week by week

The five-week roadmap

Rows are people; the integration row is shared. The course's own deadlines sit on the bottom row so every weekly report has a finished thing to show.

Critical path: G1. If the in-order pipeline slips, everything slips; the out-of-order core is joined only after the minimum system works, and the in-order bitstream is always the fallback. The out-of-order core's clock speed is the main open risk.

Know the answer before the AI writes the code

What correct looks like

This picture is a hand-drawn prediction, made before the RTL existed, to practise reading timing. The real one, cut from simulation of the actual Verilog (lock, ignored write, call, MUL stall, return, overflow and trap in 12 cycles), is diagrams/timing_diagram.svg. This is the attack caught cycle by cycle in your 3-stage pipeline. victim() is called from 0x100, its store overflows the saved return address with 0x300 (the hacked() function), and the return is caught in EX at cycle 8. If you can predict a picture like this before simulating, you can catch AI mistakes.

How to read it

Cycle 2: jal ra reaches EX, is a call, pushes 0x104. The instruction fetched behind it (0x104) is flushed, so cycle 3 has a bubble in EX. Cycle 5: the overflowing store writes 0x300 over the saved return address in data memory, which ShieldV cannot see and does not need to. Cycle 8: ret wants to jump to 0x300 but the shadow copy says 0x104, so mismatch rises, the redirect is blocked and from cycle 9 the pipeline is frozen. With protection off, cycle 9 would fetch 0x300 and the LEDs would read HACKED.

The two graded scenarios (≥25 cycles each)

Scenario 1, normal execution: nested calls in recursive Fibonacci with shadow-stack pushes and pops, a load-use stall, forwarding, a taken branch flush and a 34-cycle DIV stall.

Scenario 2, attack: the sequence above stretched to 25+ cycles, plus the trap to the handler (goal tier).

The course says timing diagrams must reflect actual execution. So generate both from your simulation VCD (WaveDrom), and capture Scenario 2 on the board with the ILA as proof.

Antigravity + Claude Code, set up for hardware

The AI build environment

Five layers, set up once on Oct 4–5 by all five of you so everyone's machine behaves the same. The AI writes most of the code. These layers make sure what it writes is checked by tools and understood by you.

Layer 1Machine
  • Laptop + Nexys A7 over USB (programming and UART on the same cable).
  • Windows: Vivado runs natively; install WSL2 Ubuntu for the open-source tools and run Claude Code there. Linux: everything native.
Layer 2Hardware tools
  • Vivado ML Standard (free, supports Artix-7 100T): synthesis, bitstream, ILA on-board debugging, utilization and timing reports.
  • Icarus Verilog for fast unit simulation, Verilator --lint-only for catching bugs before simulation, Verible for formatting.
  • GTKWave or Surfer to look at waveforms; WaveDrom + vcd2wavedrom to turn a VCD window into a report-quality timing diagram.
  • xPack riscv-none-elf-gcc (14.x or newer) to compile C for rv32im; Spike as the official reference simulator; Ripes to watch C run on a visual pipeline while learning.
  • draw.io for block diagrams, Yosys + netlistsvg to auto-draw a schematic from your RTL and cross-check the diagram; Python 3 + pyserial for scripts and reading UART.
Layer 3IDE
  • Antigravity opens the repo. Install the Claude Code extension from Open VSX (search "Claude Code"), or run claude in Antigravity's terminal. The official docs list both routes for VS Code forks.
  • From Open VSX also add a Verilog syntax extension and a Draw.io integration so diagrams live in the repo next to the code.
  • Split of AIs: Claude Code is the only writer of RTL, testbenches and scripts. Antigravity's built-in agent is the second opinion: reviewing a diff, researching a spec question, drafting a diagram. Two agents never edit the same folder at once.
Layer 4Project brain
  • CLAUDE.md: project goal, ownership, Verilog rules, commands. Claude reads it every session.
  • .claude/agents/: rtl-reviewer, tb-writer, viva-coach subagents (below).
  • .claude/skills/: timing-diagram, new-block, fpga-build, each a repeatable recipe.
  • .claude/settings.json: a hook that lints the RTL after every AI edit and sends errors back to Claude.
Layer 5Safety net
  • Private GitHub repo; one branch per block; the module owner reviews every merge into their folder.
  • GitHub Actions runs make lint test on every push, so a broken block can never sit silently in main. The run history doubles as progress evidence.
  • MCP servers are optional here. Nothing in this project needs one; hooks, subagents and CI matter far more.

CLAUDE.md starter

# ShieldV: RV32IM core with a hardware shadow stack
3-stage pipeline (IF/ID, EX, MEM/WB) on Nexys A7-100T.
ShieldV checks every return against a hardware shadow stack.
Read docs/interfaces.md before touching any port.
Interfaces are frozen; changes need all 3 owners (log in docs/decisions/).

## Ownership (one writer per folder)
rtl/core, rtl/mem          -> Member A
rtl/munit, rtl/soc, fpga   -> Member B
rtl/shield, sw             -> Member C

## Verilog rules
- Verilog-2001, one module per file, file name = module name
- Sequential: always @(posedge clk) with <= ; combinational: always @* with =
- Every register has a synchronous active-low reset (rst_n)
- No latches: assign every combinational output a default first
- Explicit widths on constants (32'd4, not 4)

## Commands
make lint | make test | make sim PROG=fib
make diagrams | make fpga

## We are learning
- Before writing a block, ask for the golden I/O table in docs/golden/.
- After a block, add 5 plain-language lines to docs/learning-log.md.
- Never call something done unless make test passes.
- Never edit a test just to make it pass.

Lint hook · .claude/settings.json

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "make -s lint 2>lint.log >/dev/null || { cat lint.log >&2; exit 2; }"
          }
        ]
      }
    ]
  }
}

After every file edit, Claude Code runs the linter. For PostToolUse, exit code 2 shows the error text to Claude, so it fixes latches and width mismatches immediately.

The learning loop, study library and viva bank

Run this loop for every block. Step 2 is the important one: you write down what the block should do before the AI writes it. When the simulation disagrees with your prediction, either the AI or your understanding is wrong, and finding out which is exactly the learning.

Learn

20 minutes on the block's study link from the map.

Predict

Write the golden input/output table and sketch the expected waveform by hand in docs/golden/.

Generate

Claude Code in plan mode: approve the plan and test cases first, then the RTL and testbench.

Prove

Lint hook, make test, compare against your prediction. Investigate every difference.

Explain

viva-coach asks 5 questions; add 5 lines to the learning log.

Commit

Separate commits for test, RTL, fix and docs. That adds up to 20+ per person without trying.

The whole method on one screen

The ShieldV framework

Five rules that hold for every block, every rung and every person, plus the definition of done every block must meet before anyone builds on it.

Contract first

Ports and memory map frozen before any logic. This is what makes parallel work possible.

Predict before generate

A human writes the expected answer; the AI writes the code; the testbench decides who is right.

Stub to start early

Every module runs against fake neighbours from day one, so nobody waits.

One rung at a time

Join one set of real blocks per step, each with a single gate test; every rung after I1 ends on the board.

Explain to own

If you can't explain a block to viva-coach, it isn't done, however green the tests are.
